# Repeated Proof Overprocessing

Read this only when reasoning depth spreads beyond the current risk, accepted
bytes are reviewed again without new evidence, broad gates rerun after every
micro-edit, or proof narration grows faster than useful work.

## Rebind The Unit

Define the current unit as one bounded decision or changed diff. Record its
artifact hash, evidence identity, acceptance rubric, risk class, and unresolved
questions. The parent program's risk controls release milestones; it does not
set the reasoning depth of every unit.

- Mechanical documentation, hashes, inventories, and workbook maintenance are
  Quick unless they authorize a risky action.
- Ordinary implementation and focused debugging are Deep when ambiguity or
  shared behavior warrants it.
- Security, tenancy, stateful migrations, external publication, deployment,
  irreversible actions, and conflicting serious evidence are Critical.

## Review Economy

Use one accountable implementer, one independent review for each materially
changed diff, and one final milestone gate. A correction receives one closure
review bound to the new bytes. An accepted review satisfies later challenge
requirements for the same artifact, rubric, and evidence.

Do not create a new review cycle because time passed, context compacted, a new
agent became available, or the same blocker remains. Reopen review only for
changed bytes, changed evidence, a newly affected risk boundary, or a new
falsifiable probe that can alter the decision.

Run focused tests while iterating and broad suites, security gates, or browser
proof at declared milestones. Append to one canonical checkpoint or receipt;
do not create a new proof document for every micro-edit.

## Hybrid Delegation

Use `$z-subagent` for bounded readers, critics, and verifiers while one
long-running implementer retains context and ownership. Add a fresh implementer
only for a genuinely independent chunk with disjoint files. The main agent
verifies decisive claims and integrates results.

If one route fails, attempt one structurally different safe route within the
stop bound. Do not spend repeated calls cosmetically varying the same route.

## Delivery Reset

Apply this when a long-running task starts spending more effort describing,
hashing, reviewing, or repartitioning work than completing the active outcome.

1. Freeze the user-visible finish line and current changed bytes.
2. Separate the real product blocker from test-fixture, host-tool, audit,
   integration, activation, and optional-improvement concerns.
3. Keep only the next direct fix, its focused proof, and the final milestone
   gate on the critical path.
4. Convert P2/P3 maintainability, progress-percentage, optional UI, monitoring,
   and future architecture findings into backlog unless explicitly required.
5. Continue reversible independent work instead of waiting for unrelated
   production certification.

Do not make mutable progress bookkeeping part of an immutable execution hash.
Keep the contract stable and update one status field or checkpoint. A checked
box, recalculated percentage, memory summary, or dispatch note must not trigger
a new packet, manifest, review, and hash cascade.

For long coupled work, prefer one context-retaining implementer and one bounded
reader or reviewer for a named question. Do not create a fresh implementer or
review cycle for every checklist section. A progress audit gets a fixed scope
and one report; it must not become a parallel product program.

## Audit Compression

Do not serialize a whole program into audit chunk -> independent verification
-> owner review before known implementation may continue. Unless release or
cutover requires a complete inventory:

1. Audit only the uncertainty that can change the next delivery action.
2. Reuse accepted source, test, browser, and runtime evidence for unchanged
   behavior; rerun baseline comparison only for a plausible regression.
3. Report progress as `DONE`, `NEXT`, and `BLOCKED` by default. Calculate
   percentages only when a concrete owner decision depends on them.
4. Put owner review at changed requirements, spend, production, irreversible
   actions, and declared milestones, not between preapproved routine chunks.
5. Keep one canonical authority. Generated session reports, topic files,
   manifests, and indexes may link to it but do not require synchronized updates.

If the audit procedure costs more than the bounded change or cannot name the
decision it unlocks, compress it before continuing.

## Stop

Stop processing when the bounded acceptance predicate is proven and no changed
risk remains. Review economy never removes a required trust-boundary,
migration, rollback, security, deployment, or live-proof gate; it removes
duplicate work that cannot change the decision.
