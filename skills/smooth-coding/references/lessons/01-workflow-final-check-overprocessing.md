# Lesson 01: Workflow Final Check Overprocessing

Read this only after the matching pattern appears. The source example produced
74 final checkpoints in five days, serialized a 13-chunk audit, and multiplied
plans, manifests, reports, topics, hashes, and reviews while product work could
still advance.

| Problem | Result or consequence | Required correction |
|---|---|---|
| Whole program marked High/Critical | Every document, hash, UI check, and code edit receives maximum ceremony | Classify each slice independently: docs are Lite, normal code is direct/Medium, and only the current migration/provider/deploy boundary receives High rigor |
| Stronger model externalizes every concern | More possibilities become tasks, gates, and blockers | Rank and discard; keep only P0/P1 findings affecting the current acceptance predicate |
| Audit-before-delivery inversion | Production work waits while the entire program is audited | Audit only uncertainty that changes the next action, then resume implementation |
| Thirteen serial review chunks | At least thirteen helper-manager-owner cycles | Group related chunks into dependency-safe execution slices and continue through the full plan |
| Owner approval after every chunk | Repeated waiting and context switching | Owner approves scope once, then reviews only changed product, spend, irreversible, and production decisions |
| Ten-step evidence matrix per chunk | Sheets, historical code, two UIs, tests, runtime, Ponytail, and scoring multiply work | Select evidence by changed risk and reuse accepted proof for unchanged behavior |
| Review recursion | Tiny or unchanged diffs receive repeated independent reviews | One stable-diff review and one closure review only after material byte changes |
| Mutable status included in hashes | Checking a box invalidates packets and starts correction loops | Hash contracts and code only; keep status and percentages outside immutable authority |
| Checklist treated as proof | Work appears complete because a box was checked without source, test, runtime, or accepted-review evidence | Check `[x]` only with a link to canonical evidence; otherwise leave `[ ]` |
| Checklist micro-granularity | Every command and file becomes another status-maintenance task | Track acceptance items or vertical slices only; use command output as evidence, not as checklist structure |
| Incomplete confused with blocked | One unknown or unfinished item freezes unrelated safe work | Keep incomplete as `[ ]`; use `BLOCKED:<external cause>` only on the dependent item and continue safe work |
| Stale checked rows | Changed code leaves old green boxes presenting false confidence | Revalidate only affected rows after material changes; preserve unchanged accepted evidence |
| Artifact fan-out | One event updates plans, manifests, topics, reports, memory, and receipts | Maintain one canonical checkpoint; generated reports are disposable indexes |
| Checkpoint inflation | Narration becomes a workstream | Checkpoint only after accepted code, a genuine blocker, a handoff, or a release transition |
| Authority diffusion | Plan, Sheet, n8n, reports, manager, helper, and memory compete as truth | Current Git plus one accepted contract is authority; everything else links to it |
| Percentage fixation | Time is spent proving a number instead of finishing | Use `DONE`, `NEXT`, and `BLOCKED`; calculate a percentage only for a real owner decision |
| Excessive chunk granularity | Small related work becomes separately reviewed programs | One vertical execution slice may satisfy several related plan chunks |
| Failed-route inflation | Tool, fixture, access, or connector failures block the whole objective | Mark `ROUTE_BLOCKED`, try one different route, and continue independent work |
| Broad gates after micro-edits | Full suites, security, and browser checks repeatedly consume hours | Focused tests during edits; broad gates once at the appropriate milestone |
| Historical baseline overuse | Two environments plus desktop/mobile proof are demanded for every UI chunk | Compare historical UI only for a plausible regression or release claim |
| Activation blocks source work | PostgreSQL/provider uncertainty freezes reversible implementation | Keep activation off while source, tests, and UI continue safely |
| Entire plan coupled into one transaction | Unrelated dependencies block each other | Preserve the full plan but execute independent slices separately and integrate serially where shared files require it |
| Too many managerial roles | Manager, THINKER, helper, reviewer, and owner repeatedly reconcile one another | One accountable implementer, one reviewer, owner at milestones |
| Large-code anxiety | Premature refactoring risks spend, receipt, tenancy, and replay safeguards | Prove behavior first, then simplify one demonstrated duplication at a time |
| Incomplete real stage chain | Planning can hide missing runtime handlers | Implement the remaining accepted handlers in dependency order; do not route around them with an invented MVP split |
| Default-off protections underused | Strong safety foundations produce no delivery advantage | Treat default-off as permission for safe source integration while activation remains gated |
| Full-plan completion gate | No fixes resume until every audit chunk finishes | Each slice closes its own criteria and immediately unlocks the next dependency-ready slice |
| Memory/report drift | Hash drift and encoding damage appear across derived copies | Verify canonical source just in time and never synchronize narrative mirrors |

Preserve tenancy, security, validation, migrations, provider spend, receipts,
idempotency, production activation, rollback, accessibility, and exact source
proof. The lesson removes duplicated process, not safeguards or owner scope.
