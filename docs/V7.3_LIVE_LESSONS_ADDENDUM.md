# V7.3 Live Lessons Addendum

Status: non-executable design lessons from prior operation. They cannot mutate
a live project or current V7 authority.

## Activation Health Versus Capacity

Report activation health separately from runtime capacity. A scheduled-job
drift may block a new activation while current Work Order, claim, resource,
worktree, and capacity gates remain valid and existing Workers continue.

## Scheduled-Job Drift Classes

Read-only doctor output distinguishes:

- `NEW_JOB`
- `COMMAND_DRIFT`
- `SCHEDULE_DRIFT`

LINKER never approves, edits, cancels, or creates a job. Diagnostics expose
stable secret-safe identities, not raw commands.

## Receipt Evidence Versus Worktree Cleanliness

A completed worktree can otherwise fail both ways: keeping canonical untracked
receipt/proof files causes `WORKTREE_NOT_CLEAN`, while moving the same verified
bytes causes `RECEIPT_SET_MISMATCH`. Do not solve this with a broad ignore or by
deleting proof.

Controller consumes the result through
`WORKER_LOCAL_PENDING -> SEALED_RESULT_EVIDENCE -> RESULT_CONSUMED`. It verifies
the complete closure, copies exact bytes to profile-scoped content-addressed
evidence, and commits a sealed manifest into snapshot/recovery truth. Only then
may cleanliness recognize exact path/hash/size-bound local residue. Every
changed, unsealed, extra, staged, tracked, or unrelated file remains fatal.

Result sealing is idempotent on exact task/event/Work Order/sealed-root identity.
Exact replay is a zero-delta no-op; altered, stale, or cross-task replay fails
closed. Evidence paths are resolved by handle within the registered worktree;
Windows device/UNC/ADS, traversal, case/8.3 alias, link/junction/reparse, and
external hard-link substitutions fail before CAS or cleanliness authority.
Crash recovery resumes one journaled sealed transition, never a second result
or generation.

Before Program import, a no-mutation preflight verifies the existing WORKER,
worktree identity, reviewed C2/HEAD, sealed evidence root, cleanliness, context,
claims, capacity, and STOP contract. Program, task, Work Order, claims, ACTION,
and snapshot are admitted atomically or none remains. This prevents a rejected
worktree from leaving an unused canonical imported packet.

Every mutable preflight predicate is revalidated under Controller lock; drift
in any one returns a precise stale/rollback result with zero durable delta.

A clean worktree at the same reviewed C2 for the same existing WORKER remains a
safe compatibility route. It does not create a replacement WORKER or transfer
authority.

## Pending Result State

When dispatch, Work Order, receipt, and proof hashes match but the Controller
has not consumed the event, expose bounded `PENDING_RESULT`. Do not collapse
this valid transition into a generic receipt mismatch or terminal success.

## Host Permission Boundary

A host permission prompt is not V7 authority or an owner product decision.
Workers may request reusable approval only for a narrow deterministic command
family and exact tool prefix. They never self-approve, request broad
PowerShell/filesystem access, or weaken the Controller security gate. Other
independent verification continues while host approval is pending.

## Worktree-Local Finalization

Preflight every helper and output path before Worker finalization. Mechanical
receipts and proof use existing worktree-local tooling and declared
`.devad/workers/...` paths. Chat approval cannot waive the host filesystem
sandbox. A blocked external temporary helper is abandoned without repeated
approval prompts or an unsafe alternate writer.

## Forwarding Is Not Consumption

A forwarded callback is not a completed Controller transition. PASS requires
the canonical event to be durably consumed, the snapshot generation/state to
advance, the completed task to clear, and the next canonical ACTION to appear.
LOOPER or an external observer must not invoke `consume-event` to make LINKER
appear autonomous.

## Three-Plane Autonomy Status

An idle LINKER and unchanged Controller generation can be healthy while a
dispatched Worker is progressing. Status reports three planes separately:

1. Controller transition and current ACTION;
2. LINKER delivery/acknowledgement; and
3. Worker phase, bounded checkpoint, STOP deadline, and unresolved decisions.

Fresh Worker progress with `ACTION=WAIT` is
`HEALTHY_WORKER_PROGRESS`, not a silent hang. It does not wake LINKER or
manufacture another ACTION. Missing progress beyond the Work Order deadline is
a diagnostic failure; a matching receipt awaiting consumption is
`PENDING_RESULT`.

## Runtime Progress Versus Activation Jobs

Doctor reports structural/runtime progress separately from activation-job
approval. An unknown or drifted job may block a new activation while valid
current Worker execution continues. The identity can be reviewed without raw
command disclosure, but no role auto-approves or mutates the job.
