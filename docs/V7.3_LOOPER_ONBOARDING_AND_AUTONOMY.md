# V7.3 LOOPER Onboarding And Autonomy

Status: candidate contract; not installed or released.

LOOPER is the human-facing lifecycle steward for one X9 installation. It makes
setup understandable, verifies the system after installation, watches bounded
autonomy proofs, and prepares versioned corrections. It is not Controller and
does not keep a project moving by secretly doing LINKER's job.

## Names

| Role | Default display name | Authority |
| --- | --- | --- |
| LOOPER | `X9 LOOPER V7.3` | Onboard, observe, diagnose, propose upgrades |
| LINKER | `AI - LINKER V7.3` | Transport one hashed ACTION and acknowledge it |
| THINKER | `AI - THINKER V7.3` | Conditional file-only judgment |
| WORKER | `AI - WORKER <profile/lane>` | Execute one bounded Work Order |
| Controller | No chat identity required | Select work and write canonical state |

`Loop Builder`, `LINX`, and `THINX` are legacy import aliases. A migration may
bind an existing task ID to the new role after validation; it never infers
authority from a title and never renames a live task in the middle of work.

## First-run experience

The installation starts in `X9 LOOPER V7.3` and proceeds in six explicit
phases.

### 1. Discover without mutation

LOOPER identifies one selected project root, current Git identity, candidate
profile continuity generations, installed X9 version, current task bindings,
required host capabilities, and conflicts. It reads no unrelated project by
default and creates no role, job, state, or remote object.

### 2. Show a dry-run plan

The user receives one compact plan containing:

- new random profile ID or explicitly selected verified restore identity;
- repository-lineage evidence and selected paths;
- proposed LINKER, THINKER, and existing WORKER bindings;
- exact files, hashes, database generations, and backup namespace;
- permissions that may be requested, using the narrowest reusable command
  family;
- temporary-home, shadow-state, migration, rollback, and removal routes; and
- what will remain unchanged.

A dry-run has no install, task creation, job registration, S3 write, provider
call, push, deploy, or product mutation.

### 3. Obtain explicit installation approval

Only an explicit owner approval advances setup. It authorizes the manifested
installation plan, not arbitrary filesystem, PowerShell, network, deployment,
or product access. A changed plan invalidates that approval.

### 4. Install and prove in isolation

The deterministic installer first uses a temporary Codex home and shadow
profile state. It verifies package hashes, schema migration, rollback,
Controller invariants, role identities, source manifests, security, and the
absence of unauthorized recurring jobs. A failed gate restores the complete
prior installation/state set and leaves evidence; it does not hotfix live
state.

### 5. Register one profile

After isolated proof, setup atomically registers profile-scoped Controller
state, LINKER, THINKER, approved existing WORKERs, claims, memory namespace,
backup namespace, evidence routes, and rollback identity. A second project gets
a different profile, state database, credentials/access point, and role
bindings under the same engine authority.

### 6. Teach safe use

The owner may talk directly to LOOPER, LINKER, THINKER, or any WORKER and may
share text, Markdown, files, images, and links. Such input cannot break the
deterministic flow: it is preserved as non-executable owner input until
Controller reconciliation emits a canonical hashed Work Order or ACTION.
LINKER never converts chat into authority by itself.

## Observe-only autonomy window

After activation LOOPER switches to `OBSERVE_ONLY`. When a WORKER produces a
canonical result, LOOPER opens one bounded observation window but performs no
state mutation or model-assisted rescue.

```text
WORKER result
  -> Controller durably consumes event
  -> snapshot/generation transitions
  -> Controller writes one hashed ACTION
  -> LINKER acknowledges and transports ACTION
  -> intended existing WORKER continues
```

Forwarding a callback is not consumption. Autonomy PASS requires every line of
that sequence, exact identities, and no external manager/LOOPER call to
`consume-event`.

LOOPER must not, during the window:

- wake LINKER, send a rescue message, or invent a NOOP/action;
- poll, sleep-loop, create a heartbeat, or call a hidden model;
- select work, edit Controller state, approve claims/jobs, or consume events;
- create a replacement WORKER or silently switch an active task; or
- interpret a plain chat message as ACTION, RESULT, or completion.

## Three-plane status

Status reports three independent planes:

| Plane | Examples |
| --- | --- |
| Controller | event pending/consumed, generation, next ACTION |
| LINKER | delivery pending, acknowledged, transported |
| WORKER | dispatched, checkpoint fresh, proof pending, result ready |

An idle LINKER and unchanged Controller can be healthy while a dispatched
WORKER has a fresh bounded checkpoint. Report `HEALTHY_WORKER_PROGRESS` without
creating another ACTION. Only an expired phase deadline or broken invariant is
a silent-hang failure.

Runtime progress and activation health are separate. An unauthorized or
drifted recurring job may block activation while an already valid bounded
WORKER flow remains structurally healthy. LOOPER reports the identities and
classification but never approves, edits, cancels, or creates jobs.

## Failure and improvement path

On failure LOOPER records the exact invariant, inputs, hashes, affected profile,
and rollback state. It prepares a minimal regression and versioned correction
in an isolated worktree, then repeats deterministic/security/review gates. It
does not patch live state or hide a LINKER/Controller defect.

Mechanical finalization preflights paths and uses existing worktree-local
scripts and proof/receipt locations. A chat approval cannot bypass the host
filesystem sandbox, and LOOPER never requests broad shell or filesystem access
to avoid one narrow permission prompt.
