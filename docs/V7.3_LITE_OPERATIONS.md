# X9 Loop V7.3 Lite Operations

Status: working-tree implementation; release, installation, and production
acceptance remain pending until the recorded test, security, migration, and
rollback gates pass.

## Where Things Live

The engine source, installed engine, and project state are separate:

```text
x9-loop source repository/
  skills/devad-x9-loop/              engine and role instructions
  scripts/                           package install, migrate, and validate tools
  templates/x9-project/.devad/       new-project overlay
  tests/                             deterministic regressions
  docs/                              operator and contributor guidance

CODEX_HOME/
  skills/devad-x9-loop/              installed engine copy
  x9-install-backups/<generation>/   package rollback copies

managed-project/
  .devad/manager/loop-lite/          sole active Loop state root
  .devad/features/                   plans, decisions, and feature evidence
  .devad/memory/                     advisory project memory
  .devad/manager/workers/            generated Worker views and routers
  .devad/workers/                    immutable Worker results and proof
```

Do not put engine code in `.devad/loop/`. Do not create a second state root.
Historical `.devad/manager/loop/` files remain evidence only and never become
routing authority.

Within `.devad/manager/loop-lite/`:

- `PROJECT_PROFILE.json` binds state and events to this project profile.
- `SNAPSHOT.json` and its referenced immutable shards are recovery truth.
- `runtime/ACTION.json` is the current Controller-selected LINKER action.
- `runtime/work-orders/` contains immutable Work Orders.
- `APPROVED_JOBS.json` is the empty-by-default recurring-job allowlist.
- `recovery/` and `MIGRATION_STATE.json` preserve migration recovery evidence.
- `loop.db`, WAL/SHM, and `runtime/` are local working artifacts. SQLite is a
  rebuildable cache during normal operation, but its exact recovery set is
  preserved while a migration is in flight.

See [Project Layout And Worktree Lifecycle](PROJECT_LAYOUT_AND_WORKTREE_LIFECYCLE.md)
for the human-safe active, retired, archived, manifest, and restore model.


Current Git bytes, the project profile, canonical snapshot/shards, Work Orders,
events, and receipts outrank chat, Markdown status views, Obsidian, or memory.

## Roles

| Role | Routine responsibility | Forbidden routine behavior |
| --- | --- | --- |
| Controller | Validate one inbox event, change canonical state transactionally, and publish at most one current action | Model calls, transport, implementation, or a second state store |
| LOOPER | Install, upgrade, observe, diagnose, and enter explicit evidence-preserving rescue after a proven fault | Selecting routine work, waking LINKER, or editing live state to hide a defect |
| LINKER | Read one canonical action, transport exact bytes, record exact acknowledgement, and stop | Scheduling, gate interpretation, code review, retries that hide a newer action, or model calls |
| THINKER | Produce predeclared file-only judgment for high-risk ambiguity | Routine scheduling, coding, transport, or automatic review |
| WORKER | Execute one immutable Work Order and emit one schema-valid result with proof | Changing scope, selecting successors, or claiming unproved security/release gates |

`Linx` and `Thinx` are legacy import/display aliases. Durable actor IDs and
registered roles, never task titles, determine identity.

## One Event Cycle

The normal path is event driven and model-free outside WORKER or predeclared
THINKER work:

```text
canonical inbox envelope
  -> loopctl.py run-once
  -> one atomic inbox/state/outbox transition
  -> current ACTION.json
  -> linker_once.py writes exact action to a durable non-waking drop
  -> linker_once.py writes the exact acknowledgement
  -> TRANSPORT_ACK envelope
  -> consume the TRANSPORT_ACK with loopctl.py run-once
  -> verify CONSUMED + DISPATCHED + old SEND is no longer current
  -> one signal-only wake: WORKER_ACTION_READY with identities/hashes only
  -> WORKER executes immutable Work Order
  -> worker_finalizer.py validates result and writes WORKER_RESULT envelope
  -> loopctl.py run-once
  -> next eligible action or deterministic WAIT/NOOP
```

Core commands use the bundled Python runtime:

```powershell
python skills/devad-x9-loop/scripts/loopctl.py --repo <project> run-once --file <inbox-event.json> --json

python skills/devad-x9-loop/scripts/linker_once.py `
  --action <project>/.devad/manager/loop-lite/runtime/ACTION.json `
  --ack <transport-ack.json> `
  --drop <adapter-drop-path> `
  --adapter-id local-file-v1

python skills/devad-x9-loop/scripts/worker_finalizer.py `
  --repo <project> `
  --result-path <project-relative-result.json> `
  --event-output <worker-result-event.json> `
  --project-profile-id <profile-id>
```

`linker_once.py` writes the acknowledgement receipt; the selected transport
adapter must publish its canonical `TRANSPORT_ACK` inbox envelope before
`run-once` consumes it. A predeclared THINKER result follows the same envelope
boundary with event type `THINX_RESULT`; the legacy event name is retained for
compatible migration.

The transport adapter must be a durable non-waking drop; it cannot wake a
Codex task or another model. Consume the TRANSPORT_ACK before sending one
`WORKER_ACTION_READY` signal-only wake with identities and hashes only. Never
paste or replay the old ACTION. The WORKER reloads durable Controller state and
the immutable Work Order, and begins only when the dispatch is `DISPATCHED`,
identities match, and STOP remains open.

An `ALREADY_CONSUMED` duplicate or delayed acknowledgement must not wake the
WORKER. A failed acknowledgement, PREPARED dispatch, mismatched identity,
expired STOP contract, or non-current action also must not wake the WORKER.

Exact duplicate events are zero-delta replays. An acknowledged old action must
republish the current action instead of hiding newer work. Invalid legacy Worker
results produce a typed `RESULT_SCHEMA_REPAIR` action for the same WORKER and
dispatch; rejected bytes remain immutable evidence.

A source-only WORKER may return `SUCCESS_CANDIDATE` when its claimed product
bytes are intentionally uncommitted and the next declared feature owns C1,
C2, security, and browser proof. During the same atomic result transition, the
Controller records each present/deleted candidate path and content hash, binds
them to the accepted result receipt, and embeds that immutable
`candidate_handoff` in the successor Work Order. If the successor uses the
same worktree, only those exact dirty paths are admitted; if it uses a separate
clean worktree, the same manifest is a read-only source reference. Receipt,
source hash, Git base, Worker, claim, or file drift blocks dispatch, and every
unrelated dirty path remains `WORKTREE_NOT_CLEAN`. LINKER never interprets the
handoff.

A terminal `CONSUMED` `WORKER_RESULT` may leave its exact canonical transport
envelope at `.devad/workers/<worker>/outbox/<event>/INBOX_EVENT.json`. Later
Work Order and candidate-handoff cleanliness checks admit only that one file
when its capped canonical bytes, event and result hashes, Worker, registered
worktree, terminal task/order/dispatch, receipt and proof identities all match
durable Controller state; the file must remain regular, contained,
non-reparse, exact-untracked, and unchanged on a second read. Absence remains
valid and admits nothing. A directory, glob, sibling file, tracked or staged
copy, tamper, or identity/status drift fails closed.

There is no polling loop, recurring heartbeat, sleep, cache warming, or model
manager in the Lite runtime. Files alone do not wake a Codex task.

## V7 To Lite Migration And Rollback

Always operate on a verified backup or shadow copy first. Record the current
HEAD, project profile/state hashes, active ACTION, database recovery set, and
Git status before migration.

```powershell
# Side-by-side V7 -> Lite state migration.
python skills/devad-x9-loop/scripts/loopctl.py --repo <project> migrate-v3 --json

# Recover deterministically after an interrupted replacement.
python skills/devad-x9-loop/scripts/loopctl.py --repo <project> recover-migration --json

# Restore the exact V7 state using the returned recovery identity.
python skills/devad-x9-loop/scripts/loopctl.py --repo <project> rollback-v7 --recovery <recovery-id> --json
```

Migration builds `.next` artifacts, validates the complete result, records a
durable journal, and only then replaces fixed active paths. It binds a project
profile and upgrades a pending V7 action without dispatching it twice. A crash
or validation failure restores the exact pre-migration V7 recovery set. Keep
the recovery generation until temporary-home installation, doctor, replay, and
rollback proof all pass.

Package rollback is separate from state rollback. Restore the timestamped
`CODEX_HOME/x9-install-backups/<generation>/` skill copy only after preserving
the failed package and its evidence.

## Worktrees And Artifacts

- **Active:** referenced by active work, claims, resources, or dispatch. It must
  exist and match its registered repository, branch, and HEAD.
- **Paused:** still live Controller state. Do not move, delete, or release its
  ownership from prose; use only a tested Controller lifecycle transition.
- **Historical/archived:** never inferred from age or folder name. A missing
  historical worktree requires proof that it owns no active task, dispatch,
  claim, or resource plus a bound owner decision hash.

Lite never resets, cleans, stashes, moves, deletes, or automatically archives a
worktree. Committed Git history is already durable; dirty bytes, receipts,
proof, and human-readable plans require an exact manifest before any later
owner-approved archive operation. A future dashboard or cold-storage module may
make this inventory easier to browse, but cannot change ownership.

## Lite Versus Deferred Pro Modules

Lite provides the deterministic kernel, project-profile binding, replay-safe
transport/finalization, V7 migration/rollback, and retained V7 safety gates.
The following remain deferred and must not be described as installed:

- selected-project S3 backup and restore;
- project-memory database, Graph/RAG, Graphify, and Obsidian views;
- one Controller multiplexing several project profiles or federation;
- advanced Orca and additional coding-agent adapters;
- read-only operations dashboard and feature/worktree cold storage; and
- public one-click onboarding and restore.

Those modules must be optional and physically removable. Orca can be an
execution adapter, Obsidian a rebuildable human view, and S3 a scoped backup
provider; none becomes Controller, state truth, or permission authority.

## Release Boundary

Before installation or GitHub push, require focused tests, one full suite,
package/template validation, Python and PowerShell syntax checks, exact staged
scope, secret scan, source-manifest verification, `git diff --check`, temporary
installation, V7 migration/rollback proof, and the self-hosted acceptance run.
Record unknown or unrun gates as `Unknown` or `PENDING`, never `PASS`.
