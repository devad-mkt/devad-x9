# V7.3 Project Continuity And Intelligence

Status: corrected candidate design; not installed or released. Statements below
are target requirements unless public proof explicitly marks them implemented.
Nothing in this document authorizes a live-project mutation, provider call,
push, deployment, recurring job, role rename, or active-skill installation.

## Decision

V7.3 adds two related but separate systems:

1. **Project continuity** preserves and restores one explicitly selected
   project, including its Codex sessions and relevant operating context.
2. **Project intelligence** builds a small, source-backed context capsule so a
   Worker finds existing settings, authorities, migrations, consumers, and
   tests before coding.

Neither system becomes Controller authority. Git, tracked `.devad` recovery
truth, canonical Work Orders, ACTION, receipts, and current runtime proof keep
their existing precedence.

## One Engine, Many Isolated Project Profiles

The V7.3 target installs one engine. One Controller authority multiplexes
isolated project profiles; each profile owns state and namespaces, never a
second Controller.

| Profile boundary | Required identity |
| --- | --- |
| Controller state and lifecycle shards | Immutable random `project_profile_id` plus profile generation |
| LINKER/THINKER task binding | Profile ID plus exact registered task ID |
| Work Orders, claims, dispatches, receipts | Profile ID plus project ID and content hashes |
| Project memory | Separate `project-memory.sqlite` and content namespace |
| Backup | Separate access identity, encryption namespace, manifest, and retention state |
| Optional agent adapters | Project-scoped capability grant and Work Order binding |

`project_profile_id` is a cryptographically random immutable identifier. Paths,
normalized remotes, repository UUIDs, Git roots, and worktrees are mutable
repository-lineage evidence only: they never create, merge, or recover profile
identity automatically. An ordinary clone receives a new profile ID. Restore
may reuse an old ID only from a verified committed continuity generation after
explicit owner selection.

Imported Codex entities retain `source_profile_id`. Thread deduplication and
collision identity is `(source_profile_id, thread_id)`, never `thread_id` alone.
A new machine may map the source profile to a local profile without rewriting
the source identity.

A small global registry may locate profiles, but it contains no task, claim,
dispatch, completion, memory fact, or backup-generation authority. Opening one
profile never loads another profile into model context by default.

### Cross-project knowledge

Cross-project access is denied by default. A project may read one fact or
artifact from another project only through an immutable federation grant that
binds Controller/owner provenance, grant ID, source and target profile/project,
purpose, object type, canonical locator, content hash, maximum bytes,
generation, issue time, expiry, revocation state, and `READ_ONLY` access. A
matching hash proves bytes, not authorization. Grants are non-transitive and
cannot be re-shared. Federation never transfers Controller, LINKER, THINKER,
Worker, approval, deployment, backup, or write authority.

### Public portability

Portable core contracts use the Python standard library, canonical files,
SQLite, and narrow provider interfaces. Codex is the reference steward. Orca,
OpenCode, Pi, Claude Code, Cursor, Graphify, Obsidian, S3-compatible storage,
and future apps are optional adapters. No adapter may become a required second
runtime, scheduler, Controller, EventStore, or truth database.

Public releases are generated from an allowlisted public schema, never by
redacting a private continuity pack. Paths and task/thread/user identifiers are
pseudonymized, and a separate public privacy/secret scan is mandatory.

### Speech-friendly roles

V7.3 uses `LOOPER`, `LINKER`, `THINKER`, and `WORKER`. The onboarding display
names are `X9 LOOPER V7.3`, `AI - LINKER V7.3`, `AI - THINKER
V7.3`, and profile/lane-specific Workers. `LINX` and `THINX` are legacy import
aliases only. Existing live tasks are not renamed in place; a validated
migration binds their exact task IDs before changing a display name. Role
identity comes from registered IDs and hashes, never speech or title.

### LOOPER lifecycle role

The first-run chat is `X9 LOOPER V7.3`. It discovers one project, shows a
dry-run profile plan, teaches the authority model, and—only after explicit
approval—uses deterministic installation to register profile state, LINKER,
THINKER, existing Workers, backup/memory namespaces, proof, and rollback. It
does not select routine work or become another Controller.

After activation LOOPER enters `OBSERVE_ONLY`. Following a Worker result,
it gives Controller and LINKER one bounded event window with no rescue prompt,
state edit, polling, hotfix, or hidden model call. A forwarded callback is not
PASS: durable event consumption, snapshot transition, one hashed next ACTION,
LINKER acknowledgement and transport, and continuation by the intended
existing Worker must all occur without LOOPER/external-manager intervention.
If the deadline or an invariant fails, LOOPER reports the exact diagnostic and
prepares an isolated versioned correction; it never calls `consume-event` or
does LINKER's or Controller's job to hide the defect.

LOOPER also preflights helper paths. Mechanical finalization uses existing
worktree-local tooling and proof/receipt paths; chat approval never bypasses the
host filesystem sandbox.

The complete first-run and observation contract is in
[V7.3 LOOPER Onboarding And Autonomy](V7.3_LOOPER_ONBOARDING_AND_AUTONOMY.md).

### Delivery priority

V7.3 is developed and simulated in an isolated checkout with synthetic
projects, fake credentials, fake S3, and fake app adapters. It must not read or
write the live project, installed V7 skill, or live Controller state during
that simulation. Current live-project lanes finish first. The later pilot is a
separately approved read-only export only; no live-profile restore occurs.

Synthetic fixtures model realistic scale, active and archived history, spawn
relationships, collisions, missing objects, and corruption without reading a
live inventory. Historical counts are planning evidence, not test constants.
Unavailable history is `MISSING` or `UNKNOWN`, never invented.

## Stable Project Selection

`PROJECT_SELECTION.json` contains the immutable profile ID, stable project ID,
repository-lineage evidence, explicit owner pins, archive policy, and one
tri-state decision per candidate thread: `INCLUDED`, `EXCLUDED`, or
`AMBIGUOUS`.

Selection uses:

1. normalized thread `cwd` under an approved project/worktree root;
2. normalized Git origin identity;
3. parent/child edges as evidence only;
4. explicit owner-pinned thread IDs; and
5. both active and archived session stores.

A parent decision never includes a child transitively; each child must match
independent project evidence or an explicit owner pin. Title, keyword, chat
text, or inferred relationship alone never yields `INCLUDED`. Every decision
records exact evidence. A generation cannot claim complete coverage while any
candidate remains `AMBIGUOUS`.

## Three Database Boundaries

| Database | Purpose | Authority |
| --- | --- | --- |
| `.devad/manager/loop-lite/loop.db` | Disposable Controller working cache | None after loss; rebuild only from tracked snapshot and shards |
| `codex-export.sqlite` | Versioned project-filtered Codex archive rows | Archive/adapter input only |
| `project-memory.sqlite` | Session, fact, evidence, attachment, skill, and search index | Advisory project context only |

`project-memory.sqlite` must not contain Controller task, dispatch, claim,
gate, delivery, approval, or completion authority. It is not live-multiwriter
sync. `codex-export.sqlite` is never direct permission to edit a live Codex
database or claim app-visible restoration. Each backup is an immutable
single-writer generation with a predecessor, content root, and conflict
detection.

## Continuity Pack

The decrypted logical pack is:

```text
PROJECT_CONTINUITY_PACK/
  PROJECT_SELECTION.json
  PACK_MANIFEST.json
  codex-export.sqlite
  project-memory.sqlite
  sessions/
  objects/
  skills/
  devad/
  repository/
  path-map/
  proof/
```

Include only:

- selected thread rows and exact rollout/session bytes with source-profile identity;
- attachments referenced by selected sessions;
- selected project memories and reviewed fact ledger;
- tracked `.devad`, Controller root snapshot, every bound lifecycle shard,
  immutable Work Orders/results/proof in their reference closure;
- relevant skills that were invoked, required by durable routing, required by
  Loop/security/restore, or explicitly pinned;
- Git branch, HEAD, origins, worktree identities, and dirty-file evidence; and
- sanitized deployment topology and backup receipt identities when approved.

Exclude raw credentials, unrelated projects, the whole attachments directory,
WAL/SHM caches, controller `loop.db`, generated indexes, provider payloads, and
unreferenced global skills.

### Versioned Codex compatibility adapter

Codex session preservation and Codex-app rehydration are separate outcomes.
`CodexCompatibilityAdapter` exposes only `describe`, `probe`,
`export_selected`, `merge_restore`, and `prove_visible`. Its receipt binds the
Codex version, App Server/API version, internal schema fingerprints, supported
operations, rollback capability, and adapter hash.

Official Codex APIs are used for enumeration and visibility proof. No currently
documented API guarantees arbitrary historical thread/attachment import into a
different profile. Therefore an unsupported or unknown version is
`ARCHIVE_ONLY`: exact session and attachment objects are restored to a
searchable recovery archive, no live Codex database is written, identity
collisions are quarantined, and status is
`PARTIAL:CODEX_IMPORT_UNSUPPORTED`. App-visible PASS is forbidden.

A future full-fidelity adapter may be enabled only for an explicitly supported
version and disposable target with transactional rollback and public proof. It
never rewrites a live database directly or infers compatibility from filenames.

### Attachment identity and path safety

Attachment identity is content SHA-256 plus source profile/thread, validated
logical reference, MIME type, byte size, and safe filename. Filename alone is
never identity. Source and restore paths reject traversal, absolute or device
paths, NT object paths, `GLOBALROOT`, unapproved UNC, alternate data streams,
reserved device names, trailing dots/spaces, case-fold and 8.3 aliases,
symlink/junction/reparse escapes, and hard-link aliases outside an approved
root. Validation uses resolved handle identity rather than string prefixes.

### Compact human-readable feature artifacts

Tracked `.devad/features` keeps only current human-readable cards, contracts,
plans, tasks, compact manifests, hashes, and the offline routing/rollback
minimum. Large screenshots, exports, research bundles, and historical evidence
use encrypted content-addressed objects. Git stores their secret-safe object
identity, hash, size, media type, availability, and restore requirement.
Hydration is explicit, bounded, hash-verified, and non-authoritative. An
unavailable object is `MISSING` or `PARTIAL`; another file is never substituted.

### Sealed result evidence and worktree reuse

Canonical result evidence moves through one Controller-owned transition:

```text
WORKER_LOCAL_PENDING -> SEALED_RESULT_EVIDENCE -> RESULT_CONSUMED
```

Before consumption, declared WORKER-local receipt/proof paths and exact hashes
remain mandatory. During `consume-event`, Controller verifies the complete
receipt/proof closure, event, task, Work Order, WORKER, claims, C1/C2, byte
sizes, and hashes. It atomically copies exact bytes into a profile-scoped
content-addressed evidence store and commits a sealed manifest into snapshot
and recovery truth.

The idempotency key is `(task_id, event_id, work_order_id, sealed_root)`.
Exact replay after `RESULT_CONSUMED` returns `RESULT_REPLAY_IDEMPOTENT` with no
database, file, ACTION, snapshot, or generation delta. A changed root, stale
Work Order, or cross-task/event replay fails closed as `RESULT_REPLAY_MISMATCH`
or `STALE_RESULT_REPLAY`. Recovery from a crash after sealing but before result
consumption resumes the same journaled transition and cannot create a second
CAS authority, result, ACTION, or generation.

After sealing, the manifest/object set is receipt truth. Git cleanliness may
subtract only local files whose path, hash, size, task, event, and sealed root
match that completed manifest. It is not a directory-wide ignore rule. Changed
proof, pending/unsealed receipt residue, staged/tracked changes, extra files,
and any unrelated dirt remain fatal. Controller never deletes proof merely to
make Git look clean; removing an unchanged local copy after sealing cannot
invalidate durable receipt truth.

Before CAS copy or cleanliness subtraction, each evidence `source_path` is a
canonical repository-relative Unicode-NFC forward-slash path resolved by handle
inside the registered worktree. Reject traversal, absolute/device/NT/UNC paths,
alternate data streams, reserved names, trailing-dot/space forms, case-fold or
8.3 aliases, symlink/junction/reparse escapes, and hard-link aliases whose file
identity is reachable outside the approved root. Rejection happens before any
CAS object, sealed manifest, receipt authority, or cleanliness state changes.

The evidence store, sealed manifest, snapshot/shards, and rollback generation
form one recovery set. Prior sealed evidence cannot satisfy a later Work Order.
Exact classifications are `VERIFIED_EVIDENCE_RESIDUE`,
`EVIDENCE_RESIDUE_HASH_MISMATCH`, `EVIDENCE_RESIDUE_UNSEALED`,
`RECEIPT_SET_MISMATCH`, and existing `WORKTREE_NOT_CLEAN`.

### Atomic program admission

Controller performs a no-durable-mutation preflight before publishing an
imported Program Packet. It verifies the registered existing WORKER, exact
worktree/repository/branch/HEAD, absence of an active dispatch, dirt limited to
optional exact sealed residue, complete context, packet caps, claims/resources,
source/evidence hashes, snapshot/shard capacity, and STOP bounds.

Program artifacts are staged as disposable non-authoritative bytes. Under the
Controller lock, Controller revalidates every mutable predicate: complete
context, claims/resources, snapshot/shard capacity, packet/source/evidence
hashes, STOP bounds, active-dispatch absence, profile/state generation, Git
fingerprint, and sealed evidence root. Program, task, Work Order,
claims/resources, ACTION, and snapshot generation are committed together or
rolled back together. A rejection leaves no canonical unused import packet.

Outcomes are `PROGRAM_WORK_ORDER_ADMITTED`, `PROGRAM_PREFLIGHT_STALE`,
`PROGRAM_ADMISSION_ROLLED_BACK`, or the existing precise worktree/context/
capacity failure. LINKER, WORKER, adapters, memory, and observers gain no
sealing, cleanliness-waiver, import, dispatch, or completion authority.

## Memory Layers

1. **Raw archive:** immutable encrypted selected session bytes and receipts.
   This is evidence and is never injected wholesale.
2. **Candidate memory:** bounded Dream-like extraction with source IDs,
   hashes, confidence, privacy, expiry, and contradiction state.
3. **Reviewed fact ledger:** small source-backed project facts and decisions.
4. **Derived indexes:** SQLite FTS, optional local vectors, graphs, Graphify,
   Obsidian views, clusters, and caches. All are rebuildable.
5. **Task context capsule:** the small deterministic subset required for one
   Work Order, validated by
   [project-intelligence-v1.md](../skills/devad-x9-loop/references/project-intelligence-v1.md).

Candidate promotion is:

```text
deterministic candidate
-> optional bounded model draft
-> preview
-> Controller/owner policy decision
-> canonical write
-> hash and receipt
-> reversible rollback
```

Dream never writes reviewed truth automatically. Distill never installs or
activates a skill automatically; it produces a tested patch candidate only.

## S3 Generation

The target supports AWS S3 and compatible stores through a narrow provider that
negotiates `CONDITIONAL_CREATE`, checksums, versioning, retention/Object Lock,
project-scope enforcement, and key-commitment capabilities. Unknown or missing
required capability blocks committed-generation PASS.

Prefix naming alone is not isolation. Each project uses separate short-lived
credentials and an S3 access point or equivalent provider-enforced scope, plus
bucket-level denial of direct bypass. Backup writer, restore reader, and
owner-controlled retention administrator are separate roles. Agents receive no
Delete, policy-change, bucket-wide List, or cross-project KMS authority.
Credentials remain in the OS/provider chain and never enter Git, SQLite, Work
Orders, prompts, logs, or the pack.

Client encryption uses an audited key-committing format, initially an AWS
Encryption SDK key-committing suite where supported—not hand-built AES-GCM.
Authenticated context binds only opaque profile, generation, object, manifest,
and algorithm versions; it never includes sensitive paths or thread details.
The encrypted manifest records suite/commitment policy, key IDs, ciphertext
hashes, and encrypted data-key metadata. Wrong key, context, or noncommitting
suite fails before plaintext release. S3-side encryption, versioning, and
Object Lock are additional defenses, not replacements.

Generation flow:

1. freeze project selection and watermarks;
2. use the SQLite online-backup API, then run `quick_check` and
   `integrity_check` plus `foreign_key_check` on every copied database;
3. export filtered Codex rows and exact selected session objects;
4. resolve attachments, skills, `.devad`, Git, and reviewed memory closure;
5. secret-scan the decrypted logical pack;
6. build a canonical manifest and content root;
7. encrypt and conditionally create immutable content-addressed objects;
8. download every object, verify ciphertext size/hash, decrypt, and verify every
   plaintext hash and the canonical manifest;
9. conditionally create `GENERATION_COMMITTED.json` last, binding predecessor,
   manifest hash, object count/root, checksums, key IDs, and capability profile.

A generation without its final commit marker is incomplete and cannot restore.
A concurrent object or marker collision is `GENERATION_CONFLICT`; multipart
ETag is never treated as a content checksum.

Retention is configurable with storage/request-cost preview. `30 daily, 12
weekly, 24 monthly, seven yearly` is only a starting preset. The latest proven
restore generation is retained until an owner-controlled policy supersedes it;
agents never delete generations directly.

## Backup Trigger

- Create a small event-driven candidate after accepted C1/C2 or another
  terminal Work Order event.
- Run the actual daily incremental sync only as an external owner-approved job
  registered in `APPROVED_JOBS.json`.
- Run a weekly integrity/read sample and a periodic real restore drill.

Loop itself gains no cron, heartbeat, poller, scheduler, or cache warmer.

## Proposed Restore Workflow — Not Implemented

The future bootstrap asks for the S3 endpoint/region/bucket/access point, credential
reference, key-recovery method, selected generation, and new project root.
It then shows one conflict/path-remap preview.

Apply only while Codex is stopped:

1. create a safety backup of the target profile and repository;
2. authenticate, download, decrypt, and verify every committed-generation object;
3. restore repository and `.devad` into staging;
4. restore project memory and exact session/attachment archives by
   `(source_profile_id, identity)`, never filename;
5. quarantine every identity conflict without overwriting target data;
6. invoke the versioned Codex compatibility adapter only in a disposable target;
   unknown/unsupported versions remain `ARCHIVE_ONLY` with no Codex DB write;
7. restore differing skill bytes disabled and report the conflict;
8. rewrite only structured path fields using `PATH_MAP.json`, never raw chat;
9. rebuild `loop.db` from tracked snapshot/shards in a shadow;
10. atomically promote only validated supported state; then start Codex and run
    app/API visibility proof when the adapter supports it.

Disk presence alone is `PARTIAL`. Missing objects, conflicting thread bytes,
unsupported Codex import, or failed app visibility cannot be reported as
`PASS`. Archive-only recovery still preserves searchable history and exact
bytes, but reports `PARTIAL:CODEX_IMPORT_UNSUPPORTED`.

## External Project Lessons

| Project | Adopt | Do not adopt |
| --- | --- | --- |
| [MGP](https://github.com/HKUDS/MGP) | Policy context, memory lifecycle, audit, capabilities, export/import profile | Gateway or reference adapter as production authority |
| [OpenClaw](https://github.com/openclaw/openclaw) | Session search, bounded recall, claims/evidence, contradictions, preview/apply promotion | Remote embeddings by default, managed Dream cron, or runtime as X9 truth |
| [MiMo-Code](https://github.com/XiaomiMiMo/MiMo-Code) | Project/checkpoint/progress separation and bounded Dream/Distill candidate patterns | Automatic Dream/Distill, recurring loop runtime, or prompt-only authority |
| [Nanobot](https://github.com/HKUDS/nanobot) | Append-only cursor history and smallest-change consolidation | Default Dream schedule or treating config tests as safety proof |
| [GraphRAG](https://github.com/microsoft/graphrag) / [Obsidian](https://obsidian.md/) | Optional structural extraction and human-readable generated views | Canonical truth, dispatch authority, or required runtime dependency |
| [Orca](https://www.onorca.dev/docs) | Optional replaceable LINKER/Worker and computer-use adapter | A second Controller, backup authority, or permission-bypass mode |

V7.3 should expose an `x9-memory-v1` profile compatible with the useful MGP
semantics without hard-depending on a young protocol implementation. A future
stateless MGP adapter may import/export this profile after conformance and
security testing. Orca uses an explicit restricted launch profile; inherited
Yolo/permission-bypass arguments and cross-project terminals are rejected.

## Implementation Order

1. Freeze corrected profile identity, tri-state selection, compatibility,
   attachment, encryption, S3 isolation, federation, public-export, LOOPER, and
   restricted-adapter contracts; obtain closure review before implementation.
2. Write RED tests using generated multi-profile fixtures with realistic scale;
   never read the live project inventory.
3. Run the simulation under an OS-level sandbox/VM or restricted account where
   live roots, credentials, network, Codex profile, and installed skills are
   not mounted or accessible. Mock-only isolation cannot PASS.
4. Implement project memory, compact feature artifacts, context capsules, and
   archive-only Codex continuity before any optional full-fidelity adapter.
5. Implement audited encrypted generations, every-object verification,
   provider capability negotiation, separate project access, corruption,
   interrupted upload, and deterministic rollback.
6. Prove LOOPER onboarding and `OBSERVE_ONLY`: forwarded callbacks must be
   durably consumed and the next ACTION transported by LINKER without rescue.
7. Test supported versions only in a disposable `CODEX_HOME`; unknown versions
   remain archive-only. Then test synthetic S3/KMS/Object Lock in an isolated
   account and restore into a nonempty disposable target.
8. After live lanes finish, run a separately approved read-only export pilot;
   no live-profile restore. Optional adapters remain removable.
